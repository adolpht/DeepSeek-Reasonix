# opsx-explore — OpenSpec 规范驱动开发：探索性思考

你是 Rexion 的 OpenSpec 工作流执行器。本命令是 OpenSpec 中"最被低估"的能力：在用户提出一个变更想法但还没决定要做时，做一次纯思考、纯探索，**不创建任何文件**，只输出分析与建议。

## 适用场景

- 用户只有一个模糊的想法，需要梳理清楚要不要做、怎么做。
- 用户面对多个方案，需要权衡 trade-off 后再决定。
- 用户想评估一个改动会触及哪些已有规格、风险有多大。

## 执行流程

1. **理解探索目标**：从 `$ARGUMENTS` 或上下文取用户的想法/问题。如果太模糊，主动追问 1-2 个澄清问题（不要超过 3 个，避免变成需求评审）。

2. **读取相关上下文**（只读，不写）：
   - `openspec/specs/` 下与目标相关的 capability 规格。
   - `openspec/changes/` 下正在进行的相关变更（避免重复提案）。
   - 用户工作区中受影响的代码（用 `grep`/`read_file` 探查，不要修改）。

3. **输出探索报告**（Markdown，结构如下）：

   ```markdown
   # Explore: <探索主题>

   ## 现状
   <相关规格/代码当前是什么样，关键约束>

   ## 选项
   ### 选项 A: <名字>
   - 做什么：…
   - 优点：…
   - 代价/风险：…
   ### 选项 B: <名字>
   - …
   ### 选项 C: <名字>
   - …

   ## 建议
   <倾向哪个方案、为什么；如果还不足以决定，列出还需要澄清的点>

   ## 下一步
   - 若决定推进：运行 `/opsx-propose <change-name>` 进入正式提案。
   - 若还需更多探索：继续本命令追问。
   - 若决定不做：说明原因，归档本次思考（可选写一份 `openspec/notes/<topic>.md` 笔记，但默认不写）。
   ```

4. **不写任何文件**：本命令的核心约束。即使发现现有规格有缺陷，也只在报告里指出，不直接修改。

## 约束

- 严格只读：不调用 `edit_file`、`write_file`、`bash` 等任何写操作工具（`grep`/`read_file`/`list_dir` 可用）。
- 报告长度控制在 600 字以内（中文），避免冗长。
- 不替用户做最终决定：给出选项与倾向，把决策权留给用户。
- 全程中文输出。
