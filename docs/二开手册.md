## 1. 项目概览

### 1.1 定位

Reasonix 是一个 **DeepSeek 原生的 AI 编码/办公 Agent**，核心设计哲学：

- **配置驱动 + 插件驱动**：主仓保持精益，能力通过配置与插件注入
- **单静态二进制**：`CGO_ENABLED=0`，所有依赖纯 Go（仅接受 TOML 解析器一个第三方依赖进入核心）
- **Cache-first**：系统提示前缀必须跨轮次字节稳定，保持 DeepSeek 前缀缓存命中
- **一个 Controller 在所有前端背后**：CLI TUI / HTTP-SSE / Wails 桌面端共用同一套会话编排

### 1.2 技术栈

| 层 | 技术 |
|---|---|
| 内核语言 | Go 1.25+（toolchain go1.26.4） |
| 前端框架 | React 18.3 + TypeScript 5.6 + Vite 6 |
| 桌面框架 | Wails v2.12（Go + WebView，无 HTTP 跳） |
| Agent 画布 | @xyflow/react v12 |
| TUI | charm.land/bubbletea v2 |
| 配置 | TOML（BurntSushi/toml） |
| 持久化 | modernc.org/sqlite（纯 Go SQLite） |

### 1.3 三种前端形态

| 前端 | 入口 | 传输 | 适用场景 |
|---|---|---|---|
| CLI TUI | `reasonix chat` / `reasonix run` | 直接调用 | 终端编码、CI/CD |
| HTTP/SSE | `reasonix serve` | SSE + REST | Web 集成、远程访问 |
| 桌面端 | `reasonix-desktop` | Wails EventsOn | 桌面办公、多 Tab |

三者都通过 `boot.Build(ctx, Options)` 装配出 `*control.Controller`，只是传入不同的 `event.Sink` 实现。

## 2. 架构总览

### 2.1 分层架构

```
cmd/reasonix/main.go            (入口，仅 os.Exit(cli.Run(...)))
        │
        ▼
internal/cli                    (子命令分发：run/chat/serve/acp/mcp/setup ...)
        │
        ▼  boot.Build(ctx, opts) → *control.Controller
internal/boot                   (★ 唯一装配点：config → Controller)
        │
        ▼
internal/control                (★ Controller：会话生命周期 + 事件流编排)
        │
        ▼  agent.Runner 接口
internal/agent                  (Agent / Coordinator：模型调用 + 工具循环)
        │
        ▼  tool.Tool + tool.Registry
internal/tool + tool/builtin    (内置工具)
internal/plugin                 (MCP 客户端 / Host)
internal/skill                  (技能加载器)
        │
        ▼
internal/event                  (★ Sink：解耦 agent ↔ frontend 的类型化事件流)
```

### 2.2 核心设计原则

1. **`boot.Build` 是单一装配点**：任何前端都应通过它获得 Controller，不要重复装配
2. **`event.Sink` 单向解耦**：agent 只 emit 事件不感知前端；前端只发命令、消费事件
3. **`Runner` 接口**：单模型（`Agent`）/双模型（`Coordinator`）可互换
4. **`tool.Tool` 接口**：内置工具、MCP 插件工具、技能工具统一抽象
5. **办公能力零侵入**：所有办公能力以独立 MCP 插件实现，主仓 `internal/` 不新增办公相关 `*.go`

### 2.3 关键依赖关系

```
boot ──→ control ──→ agent ──→ provider
  │         │          │         ▲
  │         │          ├──→ tool/builtin
  │         │          ├──→ plugin (MCP)
  │         │          ├──→ skill
  │         │          ├──→ memory (Queue)
  │         │          ├──→ evidence + instruction
  │         │          ├──→ jobs
  │         │          ├──→ sandbox
  │         │          └──→ permission (Gate)
  │         │
  │         ├──→ event.Sink   ◄── 所有事件出口
  │         ├──→ hook.Runner
  │         ├──→ checkpoint + diff
  │         └──→ plugin.Host  (hot-add/remove)
  │
  ├──→ config
  ├──→ codegraph / lsp (作为 MCP server 注入 reg)
  └──→ netclient / billing / notify / outputstyle / i18n
```

## 4. 后端内核开发

### 4.1 Controller：会话驱动中枢

`internal/control/controller.go` 的 `Controller` 是传输无关的会话驱动器，核心职责：

- 驱动会话生命周期：`Send`/`Submit`/`RunTurn`/`Cancel`/`Approve`
- 发出类型化事件流：所有动作通过 `c.sink.Emit(event.Event{...})` 单一出口
- plan 模式 / auto-approve / bypass(YOLO) 切换
- 审批桥：`requestApproval` 发 `ApprovalRequest` 事件后阻塞等 `Approve(id,...)` 应答
- 分支/快照：`Branch`/`Fork`/`Rewind`/`Summarize`

**扩展点**：`Options` 是注入新 hook / gate / sink / cleanup 的总入口。

### 4.2 Agent 执行循环

`internal/agent/agent.go` 的 `Agent.Run` 是核心循环：

```
stream → executeBatch → maybeCompact  （直到模型给出无 tool_call 的最终答案）
```

- **`stream`**：调用 provider，按 chunk 类型分发 `Reasoning`/`Text`/`ToolDispatch`/`Usage` 事件
- **`executeBatch`**：先发全部 `ToolDispatch`，再按 `partitionToolCalls` 分段——**只读工具并行（≤8），写工具串行**
- **`executeOne`** 顺序：sandbox 检查 → 重复成功保护 → plan-mode 检查 → Gate.Check → PreToolUse hook → onPreEdit 快照 → 注入 callContext → `t.Execute` → 记录 evidence → PostToolUse hook

**Coordinator（双模型）**：planner + executor 双 session，保持各自 prompt 前缀缓存稳定；planner 用只读工具做调研，输出方案交给 executor 执行。通过配置 `[agent] planner_model=...` 自动启用。

### 4.3 扩展点：新增内置工具

实现 `tool.Tool` 接口即可：

```go
// internal/tool/tool.go
type Tool interface {
    Name() string
    Description() string
    Schema() map[string]any
    ReadOnly() bool
    Execute(ctx context.Context, args map[string]any) (any, error)
}
```

可选实现 `tool.Previewer` 接入 checkpoint 快照与 diff 预览：

```go
type Previewer interface {
    Preview(ctx context.Context, args map[string]any) (*Change, error)
}
```

注册方式：

1. 在 `internal/tool/builtin/` 新建文件，定义工具结构体
2. 在 `boot.Build` 里 `reg.Add(yourTool)`，或通过 `Builtin()` 工厂注册

### 4.4 扩展点：新增事件类型

事件 `Kind` 枚举位于 `internal/event/event.go`：


### 4.5 扩展点：实现新的前端

实现 `event.Sink` 接口，调 `boot.Build`：

```go
type Sink interface {
    Emit(Event)
}

// 示例：自定义前端
func main() {
    ctx := context.Background()
    sink := event.FuncSink(func(e event.Event) {
        // 处理事件（渲染到你的 UI）
    })
    ctrl, err := boot.Build(ctx, boot.Options{
        Sink: event.Sync(sink),  // 并发安全包装
    })
    if err != nil { log.Fatal(err) }
    defer ctrl.Close()

    // 发命令
    ctrl.Submit(context.Background(), "你好")
    // 处理审批
    // ctrl.Approve(id, allow, session, persist)
}
```

参考实现：
- HTTP/SSE 范本：`internal/serve/serve.go`
- NDJSON 范本：`internal/acp/`
- Wails 桌面：`desktop/app.go`

## 5. MCP 插件开发

MCP 插件是 Reasonix 最主要的扩展方式。每个插件是独立二进制，通过 stdio 与主程序通信，使用换行分隔的 JSON-RPC 2.0。

### 5.1 插件骨架（必复制的 6 部分）

所有插件 `main.go` 遵循相同骨架（直接从 `cmd/reasonix-plugin-office/main.go` 拷贝）：

#### 1) 包头与文档注释

```go
// Command reasonix-plugin-mine is an MCP stdio server exposing <工具> capabilities.
//
// Configure in reasonix.toml:
//
//   [[plugins]]
//   name = "mine"
//   command = "reasonix-plugin-mine"
//
// Tools are namespaced as mcp__mine__<tool>.
package main
```

#### 2) main() 入口（极简）

```go
var version = "dev"  // 通过 -ldflags "-X main.version=..." 覆盖

func main() {
    log.SetPrefix("reasonix-plugin-mine: ")
    log.SetFlags(0)
    if err := serve(os.Stdin, os.Stdout); err != nil {
        log.Fatal(err)
    }
}
```

**关键**：stdout 专用于 JSON-RPC，日志走 stderr。

#### 3) JSON-RPC 帧结构（逐字复制）

```go
type request struct {
    JSONRPC string           `json:"jsonrpc"`
    ID      *json.RawMessage `json:"id"`   // nil ⇒ notification（无回复）
    Method  string           `json:"method"`
    Params  json.RawMessage  `json:"params"`
}
type response struct {
    JSONRPC string          `json:"jsonrpc"`
    ID      json.RawMessage `json:"id"`
    Result  any             `json:"result,omitempty"`
    Error   *rpcError       `json:"error,omitempty"`
}
type rpcError struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
}

const protocolVersion = "2024-11-05"
const codeMethodNotFound = -32601
const codeInvalidParams  = -32602
```

#### 4) serve() 读-分发-回复主循环

```go
func serve(in *os.File, out *os.File) error {
    r := bufio.NewReader(in)
    w := bufio.NewWriter(out)
    defer w.Flush()
    for {
        line, err := r.ReadBytes('\n')
        if len(line) > 0 {
            if rerr := handleLine(line, w); rerr != nil { return rerr }
            if ferr := w.Flush(); ferr != nil { return ferr }
        }
        if err != nil { return nil }  // EOF = 干净关闭
    }
}
```

#### 5) handleLine() 方法分发

```go
func handleLine(line []byte, w *bufio.Writer) error {
    var req request
    if err := json.Unmarshal(line, &req); err != nil { return err }
    if req.ID == nil { return nil }  // notification，不回复

    resp := response{JSONRPC: "2.0", ID: *req.ID}
    switch req.Method {
    case "initialize":
        resp.Result = map[string]any{
            "protocolVersion": protocolVersion,
            "capabilities": map[string]any{"tools": map[string]any{}},
            "serverInfo": map[string]any{"name": "reasonix-plugin-mine", "version": version},
        }
    case "tools/list":
        resp.Result = map[string]any{"tools": toolList()}
    case "tools/call":
        result, rerr := callTool(req.Params)
        if rerr != nil { resp.Error = rerr } else { resp.Result = result }
    default:
        resp.Error = &rpcError{Code: codeMethodNotFound, Message: "method not found: " + req.Method}
    }
    return json.NewEncoder(w).Encode(&resp)
}
```

#### 6) toolDef 注册表与分发

```go
type toolDef struct {
    name        string
    description string
    schema      map[string]any
    readOnly    bool
    run         func(args map[string]any) (any, error)
}

var tools = []toolDef{ /* 你的工具 */ }

func toolList() []map[string]any {
    out := make([]map[string]any, len(tools))
    for i, t := range tools {
        out[i] = map[string]any{
            "name":        t.name,
            "description": t.description,
            "inputSchema": t.schema,
            "annotations": map[string]any{
                "readOnlyHint": t.readOnly,  // ★ 决定并行调度 + 自动放行
                "title":        t.name,
            },
        }
    }
    return out
}

func callTool(params json.RawMessage) (any, *rpcError) {
    var p struct {
        Name      string         `json:"name"`
        Arguments map[string]any `json:"arguments"`
    }
    if err := json.Unmarshal(params, &p); err != nil {
        return nil, &rpcError{Code: codeInvalidParams, Message: err.Error()}
    }
    for _, t := range tools {
        if t.name == p.Name {
            result, err := t.run(p.Arguments)
            if err != nil { return textResult(err.Error(), true), nil }
            return result, nil
        }
    }
    return nil, &rpcError{Code: codeMethodNotFound, Message: "unknown tool: " + p.Name}
}
```

### 5.2 工具 Schema 声明

### 5.4 参数解析 helper（逐字复制）

```go
func argString(args map[string]any, key string) (string, error) {
    v, ok := args[key]
    if !ok || v == nil { return "", fmt.Errorf("missing required argument: %s", key) }
    s, ok := v.(string)
    if !ok { return "", fmt.Errorf("argument %s must be string, got %T", key, v) }
    return s, nil
}

func argStringDefault(args map[string]any, key, def string) string {
    if v, ok := args[key].(string); ok && v != "" { return v }
    return def
}

func argIntDefault(args map[string]any, key string, def int) int {
    // JSON 数字总是 float64
    if v, ok := args[key].(float64); ok { return int(v) }
    return def
}
```

### 5.5 readOnlyHint 的关键作用

在 `annotations.readOnlyHint` 声明 `readOnly: true` 后，**同时触发两个效果**：

1. **并行调度**：agent 把多个 readOnly 工具并行批量执行（≤8）
2. **权限自动放行**：`Policy.Decide` 对 readOnly 工具的 fallback 永远是 `Allow`，不弹审批

| readOnly | 调度 | 默认权限 |
|---|---|---|
| `true` | 并行 | Allow（自动放行） |
| `false` | 串行 | Ask（弹 ApprovalModal） |

**典型例子**：`read_docx`/`read_sheet`/`query_sheet`/`web_extract` = true；`write_docx`/`send_mail`/`add_event` = false。

### 5.6 审批机制

审批流转链路：

```
插件工具调用
   ↓
internal/permission/permission.go  (Policy.Decide 纯规则评估)
   ↓ deny > ask > allow > fallback
   ↓ readOnly=true → fallback=Allow（自动放行）
   ↓ readOnly=false → fallback=Mode(默认Ask)
   ↓
internal/permission/Gate.Check()  (Ask 分支调用 Approver)
   ↓
internal/control/controller.go (gateApprover 适配器)
   ↓ requestApproval() 发 ApprovalRequest 事件
   ↓
前端 ApprovalModal 渲染（desktop）/ chat_tui 渲染（CLI）
   ↓ onAnswer(allow, session, persist)
   ↓
Controller.Approve(id, ...) 回复
```

桌面端 ApprovalModal 对普通工具提供 4 选项：
- `1` 本次允许
- `2` 本会话允许同类
- `3` 总是允许（持久化到配置）
- `4` 拒绝

**plan 审批特殊机制**：用户批准 plan 后，本次执行轮内所有写操作自动放行（`autoApprove=true`），执行完再复位。

### 5.7 go.mod 依赖管理

项目存在两种模式：

| 模式 | 适用 | 说明 |
|---|---|---|
| 主模块内（无独立 go.mod） | example/office/sheet/mail/im | 用主 `go.mod`，一次 `go build` 即可 |
| 独立 go.mod | calendar/slides/search | 隔离重型/商业依赖（sqlite/unioffice/excelize） |

**决策原则**：仅当引入了重型/商业依赖时才拆分独立 go.mod；否则留在主模块更简单。

Makefile 构建命令对两种模式统一：

```makefile
CGO_ENABLED=0 go build -ldflags "$(LDFLAGS)" -o bin/reasonix-plugin-mine ./cmd/reasonix-plugin-mine
```

### 5.9 配置接入

插件二进制构建后，在 `reasonix.toml` 声明：

```toml

name    = "mine"
command = "reasonix-plugin-mine"
# 可选字段：
# args      = ["--flag"]
# env       = { MY_KEY = "value" }
# type      = "stdio"        # 默认；也支持 http/sse
# url       = "http://..."   # http/sse 模式
# headers   = { Auth = "Bearer ${MY_TOKEN}" }
# auto_start = true
```

**Tier 分级**：
- `eager`：阻塞主程序启动直到握手完成（系统提示词依赖其工具时用）

- `lazy`：注册占位工具，首次模型调用时才 spawn

## 6. 技能与命令系统

### 6.1 skills/ vs commands/ 的核心区别

这是本项目最重要的区分点：

| 维度 | `.reasonix/skills/` | `.reasonix/commands/` |
|---|---|---|
| 加载器 | `internal/skill`（`skill.Store`） | `internal/command`（`command.Load`） |
| frontmatter 字段 | `name`/`description`/`runas`/`allowed-tools`/`model`/`effort` | `description`/`argument-hint` |
| 执行模式 | inline（折叠进父轮）或 subagent（隔离子代理） | 渲染 body 作为下一轮 user turn |
| 工具作用域 | subagent 支持 `allowed-tools` 白名单 | 无工具限制 |
| 调用方式 | `run_skill({name, arguments})` 工具 或 `/<name>` | `/<name>` |
| 进系统提示索引 | 是（names + descriptions 进入 cache-stable 前缀） | 否 |

**关键约束**：放在 `commands/` 下会**无法识别** `runas` 和 `allowed-tools`。subagent 工作流技能必须在 `.reasonix/skills/`。

### 6.2 技能发现根（优先级从高到低）

1. **项目作用域**：`<projectRoot>/{.reasonix,.agents,.agent,.claude}/skills/`
2. **自定义路径**：`[skills].paths` 配置
3. **全局作用域**：`<homeDir>/{.reasonix,.agents,.agent,.claude}/skills/`
4. **内置**：`internal/skill/builtins.go`

`ConventionDirs = []string{".reasonix", ".agents", ".agent", ".claude"}`（定义于 `internal/config/config.go:1560`），兼容其他 Agent 工具的技能。

### 6.3 技能文件布局

两种形态：

- **目录布局**：`<name>/SKILL.md`，可带 `references/*.md`（Anthropic Skills 兼容，自动追加到 body）
- **扁平布局**：`<name>.md`

扫描行为：MaxDepth 默认 3（最大 5），跳过 `.` 开头目录、`assets`/`node_modules`/`references`/`scripts`，跟随符号链接。

### 6.4 Frontmatter 字段

```yaml
---
name: weekly-report
description: 基于最近 7 天 git log 生成周报 docx
runas: subagent              # inline | subagent（context: fork 或 agent: <x> 也被识别为 subagent）
allowed-tools: bash, read_file, mcp__office__write_docx
model: deepseek-chat         # 可选，覆盖子代理模型
effort: medium               # 可选，覆盖 effort
---
```

### 6.5 Subagent 工作流机制

`runas: subagent` 的技能被调用时：

1. `run_skill.Execute` 检测到 `RunSubagent` 模式
2. 调用 `runner(ctx, sk, rawArgs)` — 启动**隔离子代理循环**
3. 子代理以技能 body 作为 system prompt，`arguments` 作为唯一输入
4. **子代理的工具调用和推理永不进入父上下文**，只返回最终答案
5. 工具集按 `allowed-tools` 过滤，并剔除 meta-tool（`task`/`run_skill`/`spawn_agent`/...），**保证嵌套只有一层**

设计意图：隔离长任务、保护主会话上下文、保持 system prompt 前缀 cache-stable。

### 6.6 内置技能（16 个）

- `init` — 生成/刷新 `AGENTS.md` 项目记忆
- `install-capability` — 安装/卸载 MCP 服务器和技能
- `test` — 运行测试套件、诊断失败、应用修复、重跑直到绿色

**Subagent 内置技能**：
- `explore` — 只读代码库探索
- `research` — web_fetch + 代码阅读研究
- `review` — 代码审查（当前分支 diff）
- `security-review` — 安全视角审查
- `analyze-project` — 分析老旧项目生成文档体系
- `doc-reviewer` — 审查并修复 analyze-project 产出

### 7.2 多 Tab 架构

每个 Tab 持有独立的 `control.Controller`：

```go
// desktop/app.go
tabs map[string]*WorkspaceTab   // tabId → tab 运行时
```

前端通过 `statesRef = useRef<TabStates>(new Map())` 维护 per-tab state，事件 payload 携带 `tabId` 精确路由。

### 7.3 事件机制（Wails EventsOn，非 SSE）

**后端发出**：

```go
// desktop/app.go
runtime.EventsEmit(ctx, "agent:event", wireEvent)
```

**前端订阅**：

```typescript
// lib/bridge.ts
export const EVENT_CHANNEL = "agent:event";  // 必须与 app.go 一致

export function onEvent(cb: (e: WireEvent) => void): () => void {
  return runtime.EventsOn(EVENT_CHANNEL, cb);
}
```

**事件路由**（`lib/useController.ts`）：

```typescript
onEvent((e) => {
  const tabId = e.tabId || activeTabIdRef.current;
  dispatchTo(tabId, { type: "event", event: e });
});
```

其他事件 channel：
- `updater:progress` — 自动更新进度
- `agent:ready` — Wails 后端就绪
- `project-tree:changed` — 项目树变更

### 7.4 wire 格式与 SSE 对齐

`desktop/wire.go` 的 `wireEvent` 结构**镜像** `internal/serve/wire.go` 的 SSE 字段。这意味着桌面端和 CLI/Web 端共享同一套事件契约，只是传输层不同（Wails Events vs SSE）。

`kindNames` map 将 `event.Kind` 枚举映射为稳定字符串：`turn_started`/`reasoning`/`text`/`tool_dispatch`/`tool_result`/`approval_request`/`turn_done`/...

### 7.5 前后端契约保障（编译期）

`lib/bridge.ts` 的 `AppBindings` 接口与 Wails 生成的 `GeneratedApp` 双向 drift check：

```typescript
type _CheckGenToApp = AssertNever<Exclude<keyof typeof GeneratedApp, keyof AppBindings>>;
```

编译期确保前端调用签名与后端绑定方法完全一致。

### 7.6 Proxy 懒解析 + 浏览器 mock

`window.go.main.App` 在 Wails 环境外不可用，`bridge.ts` 用 Proxy 懒解析，失败回退到完整 mock，支持纯浏览器 `pnpm dev`：

```typescript
export const app = new Proxy({} as AppBindings, {
  get(_t, prop) {
    const gen = window.go?.main?.App;
    if (gen && typeof (gen as any)[prop] === "function") {
      return (gen as any)[prop].bind(gen);
    }
    return (mockSingleton as any)[prop];
  },
});
```

### 7.9 国际化机制

`locales/zh.ts` 和 `locales/en.ts` 用 `Record<DictKey, string>` 注解**编译期强制键集一致**：

```typescript
export const zh: Record<DictKey, string> = { ... };
```

占位符语法：`{placeholder}`，由 `i18n.translate(locale, key, vars)` 填充。

缺键回退：当前 locale → en → 原始 key 字符串。

### 7.10 主题系统

- `data-theme`：`auto` / `light` / `dark`
- `data-theme-style`：9 种 style（graphite/ember/aurora/midnight/sandstone/porcelain/linen/glacier/office）

style → resolved theme 映射：
- dark 阵营：graphite / ember / aurora / midnight
- light 阵营：sandstone / porcelain / linen / glacier / office

`applyTheme(theme, style)` 同步设置 `dataset` + 调用 `WindowSetDarkTheme`/`WindowSetLightTheme`/`WindowSetSystemDefault` 同步原生窗口标题栏。

`getThemeForWorkspaceType(wsType)`：coding → dark+graphite，office/assistant → light+office。当 `workspaceType` 变化时自动切换（除非启用 unified theme，localStorage key `"reasonix-unified-theme"`）。

`initTheme()` 在 React mount 前调用，避免首帧闪烁。

```toml
# auto_start = true

[[agents.custom_roles]]       # 自定义 spawn_agent 角色
name = "analyst"
read_only = true
system_addon = "你是一名数据分析师"
```

### 9.3 .mcp.json 兼容

项目根 `.mcp.json` 被读取并合并到 `[[plugins]]`，**字段对字段映射 Claude Code 的 mcpServers 规范**——给 Claude Code 配的 MCP 服务器在 Reasonix 里开箱即用。

### 9.4 环境变量

`.env` 只存放密钥；Provider 的 `base_url`/`model` 配置在 `reasonix.toml`，通过 `api_key_env` 字段指向环境变量。密钥永不写入配置文件。

```bash
# .env
DEEPSEEK_API_KEY=sk-...
MIMO_API_KEY=...
```

`PluginEntry.ExpandedPlugin()` 支持 `${VAR}` 和 `${VAR:-default}` 展开。

### 9.5 ConventionDirs

```go
var ConventionDirs = []string{".reasonix", ".agents", ".agent", ".claude"}
```

技能/命令/项目记忆（`REASONIX.md`/`AGENTS.md`）在这四种约定目录下都被扫描，兼容其他 Agent 工具。

### 9.6 配置层级覆盖

- project `./reasonix.toml` > user `~/.config/reasonix/config.toml`
- 同名 skill/command：project > custom > global > builtin
- plugins/providers 在 `reasonix.toml` 里声明

## 11. 工程约定与规范

### 11.1 设计原则（来自 SPEC.md）

1. **配置/插件驱动**：主仓保持精益，能力通过配置与插件注入
2. **单静态二进制**：`CGO_ENABLED=0`，所有依赖纯 Go
3. **两层扩展**：编译期 `init()` 自注册 + 运行时 MCP 插件
4. **接口先行**：`Provider`/`Tool` 是接口；内置子包通过 `init()` 自注册，父包永不导入子包
5. **办公能力零侵入**：所有办公能力以独立 MCP 插件实现，主仓 `internal/` 不新增办公相关 `*.go`
6. **演进不过度工程**

### 11.2 语言约定

- 代码/注释/用户可见串/系统提示均为英语
- README 双语（`README.md` 英文 + `README.zh-CN.md`）
- 用户沟通语言跟随用户最新消息

### 11.3 命名规范

| 类别 | 规范 | 示例 |
|---|---|---|
| Go module | `reasonix`（主）/ `reasonix/desktop`（桌面）/ `reasonix-plugin-<func>`（独立插件） | `reasonix-plugin-sheet` |
| MCP 插件二进制 | `reasonix-plugin-<function>` | `cmd/reasonix-plugin-office/` |
| MCP 工具命名空间 | `mcp__<server>__<tool>`（空格归一为 `_`） | `mcp__office__write_docx` |
| 技能名 | 字母/数字/`_`/`-`/`.`，1-64 字符，字母数字开头 | `weekly-report` |
| 技能文件 | 扁平 `<name>.md` 或目录 `<name>/SKILL.md` | `.reasonix/skills/weekly-report.md` |
| 斜杠命令 | `/review`；子目录 `git/commit.md` → `/git:commit` | `.reasonix/commands/review.md` |
| Commit 消息 | Conventional Commits | `feat(glob): add ** recursive pattern support` |
| 分支 | `main-v2`（活跃）/ `v1`（维护） | — |
| Tag | `v*`（CLI）/ `desktop-v*`（桌面） | `v1.0.0` |

### 11.4 代码风格

- `gofmt` + `go vet` 必须干净
- 导出标识符必须文档注释
- 错误处理：库代码 `fmt.Errorf("...: %w", err)` 返回，永不 `os.Exit`/print；只有 `cli`/`main` 决定退出码
- `internal/` 包规则：每个包文档化其关注点
- `desktop/` 是独立模块，父模块 `go build/test ./...` 跳过它

### 11.5 Cache-first 约定（最重要）

系统提示前缀（base prompt + tools + memory）必须跨轮次**字节稳定**，保持 DeepSeek 前缀缓存命中。

**二开改 prompt 时要避开运行时改前缀**：

- memory/skills index/outputstyle 都折入 cache-stable 前缀
- mid-session 变更走 `pendingMemory`/`Queue` 注入 turn 尾而非改前缀
- `SetPlanMode` 只切 gate 不改 prompt

### 11.6 副作用约定

- 写文件等副作用走 `ApprovalModal.tsx` 审批机制
- `readOnly: true` 工具自动放行；`readOnly: false` 默认弹审批
- 项目级 hook 需 `/hooks trust` 显式信任，防克隆仓库静默执行

### 11.7 子代理单层嵌套约束

`task`/`spawn_agent` 等通过 `SubagentMetaTools()` + `agentMetaTools` 列表强制子代理看不到这些 meta-tool，保证嵌套深度 = 1。自定义 spawn 工具要遵循此约束。

### 11.8 MCP 工具命名空间

`mcp__<server>__<tool>`，`Host.Remove` 时按前缀整批撤销。自定义工具不要用此前缀以免冲突。

### 11.9 会话持久化约定

- `.jsonl` 存消息
- `.meta` 存分支树
- `.ckpt/` 存快照
- `archive/` 存压缩归档

二开新会话操作要走 `controller.Snapshot/SnapshotActivity` 而非直接写文件。

### 11.10 finalReadinessCheck

模型给最终答案前，host 会校验项目 memory 里声明 `verify` 的命令是否在最近写操作后跑过、`complete_step` 是否调用、todo 是否全完成。

二开可在 `REASONIX.md` 里加 `- verify: <cmd>` 行让 host 强制校验。

### 11.11 防死循环闸

- `stormSig`/`repeatSuccessCounts`：防止工具调用死循环
- 自定义工具若返回错误，错误信息不要包含可变参数（否则签名每次不同，闸失效）

## 12. 常见二次开发场景

### 12.1 场景：新增一个办公能力插件

**需求**：添加一个处理 PDF 的插件。

1. 新建 `cmd/reasonix-plugin-pdf/main.go`，从 office 拷贝骨架
2. 修改 `serverInfo.name = "reasonix-plugin-pdf"`
3. 实现工具（如 `read_pdf`/`write_pdf`/`pdf_to_docx`），每个工具一个 `.go` 文件
4. 判断 `readOnly`：`read_pdf` = true，`write_pdf` = false
5. 在 Makefile 的 `build` target 加：
   ```makefile
   CGO_ENABLED=0 go build -ldflags "$(LDFLAGS)" -o bin/reasonix-plugin-pdf ./cmd/reasonix-plugin-pdf
   ```
6. 在 `reasonix.toml` 加：
   ```toml
   [[plugins]]
   name = "pdf"
   command = "reasonix-plugin-pdf"
   ```
7. 写 `cmd/reasonix-plugin-pdf/README.md`
8. （可选）创建对应 Skill：`.reasonix/skills/pdf-extract.md`，`runas: subagent`，`allowed-tools: bash, read_file, mcp__pdf__read_pdf`

### 12.2 场景：新增一个桌面前端面板

**需求**：添加一个"数据看板"面板。

参考 [7.8 新增面板/导航项完整流程](#78-新增面板导航项完整流程)。

### 12.3 场景：新增一个自定义 Agent 角色

```toml
# reasonix.toml
[[agents.custom_roles]]
name = "analyst"
read_only = true
system_addon = "你是一名数据分析师，专注于数据清洗和统计分析"
```

然后通过 `spawn_agent` 工具使用：

```
spawn_agent({ role: "analyst", task: "分析这份销售数据" })
```

### 12.4 场景：接入一个新的 LLM Provider

参考 [8.3 新增 Provider](#83-新增-provider)。

### 12.5 场景：添加项目级 Hook

在 `reasonix.toml` 配置：

```toml
[[hooks]]
event = "PreToolUse"
command = "echo 'tool used' >> /tmp/tool.log"

[[hooks]]
event = "UserPromptSubmit"
command = "echo 'prompt submitted' >> /tmp/prompt.log"
```

项目级 hook 需 `/hooks trust` 显式信任（防克隆仓库静默执行）。

支持的事件：`PreToolUse`/`PostToolUse`/`PostLLMCall`/`SubagentStop`/`PreCompact`/`SessionStart`/`SessionEnd`/`UserPromptSubmit`/`Stop`/`Notification`。

### 12.6 场景：添加权限规则

```toml
[permissions]
mode = "ask"                 # 全局默认
deny = ["bash rm -rf"]       # 永久拒绝
allow = ["read_file"]        # 永久允许
ask = ["write_file"]         # 必须询问
```

交互式可"always allow"持久化（选项 3）。

### 12.7 场景：把 Reasonix 作为 MCP Server 暴露

```bash
reasonix mcp-server
```

其他 MCP 客户端可调用 Reasonix 的能力。参考 `internal/mcpserver/server.go`。

### 12.8 场景：接入编辑器（Zed/VSCode）

使用 ACP（Agent Client Protocol）：

```bash
reasonix --acp
```

实现 NDJSON JSON-RPC 客户端，参考 `internal/acp/server.go`。

### 12.9 场景：添加压缩策略

```toml
[agent]
soft_compact_ratio = 0.5     # 软阈值，开始提示
compact_ratio = 0.8          # 触发压缩
compact_force_ratio = 0.9    # 强制压缩
recent_keep = 10             # 保留最近 N 条
```

### 12.10 场景：暴露自定义工具给子代理

```go
// 在 boot.Build 后
skill.SetExtraReadTools(reg, []tool.Tool{myCustomReadTool})
```

或在 Skill frontmatter 用 `allowed-tools` 白名单：

```yaml
allowed-tools: bash, read_file, mcp__office__write_docx, my_custom_tool
```
